## 1. 第一眼最大的差距：鱼的「体量感」与「数量感」

### 1.1 客观量（均取画面短边的百分比，短边 = 视口高度）

| 画面 | 鱼的典型体长 / 短边 | 依据 |
|---|---|---|
| **A 用户参考画** | ≈ **7%** | 特写目测换算（±2pp） |
| **B 项目设计稿** | ≈ **13%** | 同上 |
| **C 当前实现** | ≈ **16%（顶格）** | 代码精确值，见下 |

**★ 需求自己的 STAGES 表（`eco/constants.js:30-38`）是这样分的** —— 但注意单位：

| 阶段 | 日龄 | 体长占**自身上限**（`lengthCm / lCapCm`） | **折算到「占视口短边」**（`L_cap = 25cm` 时） |
|---|---|---|---|
| 鱼苗 fry | 0–17 | 2% – 10% | **0.3% – 1.3%** |
| 幼鱼 juvenile | 17–60 | 10% – 33% | 1.3% – 4.4% |
| 亚成体 subadult | 60–111 | 33% – 76% | 4.4% – 10.1% |
| 成体 adult | 111–163 | 76% – 96% | 10.1% – 12.8% |
| 老鱼 elder | 163+ | **100%**（F-7.2.5 入阶钳制） | 13.3%（`L_cap = 30` 时 16%） |

> ⚠️ **单位陷阱（本文档初稿在这里写错过一次，已更正）**：`STAGES.minFrac / maxFrac` 是
> **「占自身上限」**，不是「占视口短边」。校验：`lBirthCm = 0.6cm`、`L_cap ≈ 25cm`
> ⇒ 出生占比 `0.6 / 25 = 2.4%`，正好对上 fry 的 `minFrac = 0.02`。
> 折算关系：`占短边 = frac × L_cap × 0.16 / L_global(30) = frac × L_cap / 187.5`。

⇒ 由这张表算出来的实际画面尺度是：

| 画面 | 折算结果 |
|---|---|
| **A 用户参考画** ≈7% 短边 | 对应 `lengthCm ≈ 13cm` ⇒ **幼鱼末 / 亚成体初** |
| 当前实现 ≈16% 短边 | 对应 `lengthCm = 30cm` ⇒ **老鱼满格**（`lifecycle` 把 elder 全部钳到 `L_cap`） |

所以准确的说法不是「A 是一池鱼苗」，而是：**A 是一池「还没长大的鱼」**——
大量幼鱼/亚成体尺度、半透明、成群；当前实现是**一池老鱼**（`lCap` 顶格、不透明、各游各的）。
方向是对的，只是「7%」落在幼鱼带而不是鱼苗带。

**当前实现为什么看起来「全是大鱼」**：F-7.2.2 规定最大个体 ≤ 短边 **16%**；`C28` 定义
`pxPerCm = min(W,H) × 0.16 / L_global`，`L_global` 默认 30cm
⇒ `lengthCm = 30` 时体长 px 恰好 = 短边 × 0.16，也就是**设计上限本身**。
而 `lifecycle` 又通过 F-7.2.5 把**所有老鱼**钳到 `L_cap` —— 个体尺度是分布开的，
但**渲染层完全不知道阶段**（下面 §1.2），于是把它们一律按成鱼画出来。
实测（60 池塘日推演）池中确有 `fry 0.3% / juvenile 1.3% / subadult 2.5% / adult 4.7% / elder 11.3%` 的完整金字塔，
只是**从不体现在画面上**。

### 1.2 但「看起来不一样」不只是尺寸

A 的观感 = **半透明 + 紧密群游**。这两条是需求明文，不是我的主观偏好：

- `REQUIREMENTS_v4.md:132` / `:230`：**鱼苗 = 近半透明，紧密群游，躲水草阴影**
- `src/engine/eco/constants.js:32`：`{ key: 'fry', name: '鱼苗', from: 0, to: 17, minFrac: 0.02, maxFrac: 0.10 }` —— 常量抄了

实测落地情况：

| 检查 | 结果 |
|---|---|
| `koi-renderer.js` 是否读过 `fish.stage` | **0 命中** ⇒ 渲染层完全不知道鱼处于哪个阶段 |
| 全项目搜「群游 / school / 抱团」 | **0 命中** ⇒ 群游行为不存在 |
| `globalAlpha` 的来源 | `fish.depth`（景深）+ 夜间 + 死亡淡出，**与阶段无关** |

⇒ **这不是「鱼画得不好」，是「种群结构没有反映到画面上」**。
生态侧算得清清楚楚（`STAGES` 五档、体长占比 2%–60%、死亡/孵化闭环），
渲染侧只拿到一个 `length`。所以「画面里全是成年鱼」。

> 这一条与 `docs/GAP-ANALYSIS.md` #7 是同一件事，但 GAP-ANALYSIS 把它记成「鱼苗半透明未做」；
> 实际范围更大 —— 缺的是**整条「阶段 → 外观」通路**（#6 老鱼褪色 / #7 鱼苗半透明 / #8 幼鱼花纹显现 三条同源）。

## 2.1 本轮落地：C 方案（阶段 → 外观 + 群游 + 卵群）

**用户拍板的 C 方案**：保留设计稿的近景尺度（**不动 F-7.2.2 的 16% 口径**），
把**已经算好的种群结构画出来** —— 让画面在长鱼苗/幼鱼的那几格自己接近参考画的观感。

### 落地的三条通路

| 通路 | 数据侧（`eco/`） | 翻译层（`eco-bridge.js`） | 渲染/行为侧 |
|---|---|---|---|
| 阶段 → 外观 | `stage` / `ageDays` | `updateFishLook()` → `aFade` / `aPattern` / `aPale` 三个**纯数字** | `koi-renderer.js` 只做乘法（不认识"鱼苗"这个词） |
| 阶段 → 行为 | `stage` | 查 `SCHOOL` 两张表（权重 / 分离倍率） | `simulation.js` 的 O(n²) 邻居循环 |
| 卵 → 视图 | `world.eggs`（无坐标） | `clutchAnchor()` + `eggVisual()`（id 派生确定性位置） | `pond.drawEggs()` |

### 实测数字（`npm run check:stage-look`，47/47 通过）

| 项 | 数值 | 判据 |
|---|---|---|
| 鱼苗出生即半透明 | `aFade 0.52` | §6 鱼苗「近半透明」 |
| 鱼苗几乎无斑 → 60 日全显 | `aPattern 0.16 → 1.00` | §6 幼鱼「花纹显现」（17 日边界两侧连续，不闪） |
| 老鱼褪色封顶 | `aPale → 0.34`（青白，不是纯白） | §6 老鱼「体色褪淡」 |
| 鱼苗抱团 | 公平对照 **0.52**（5 个种子 0.52–0.62） | < 0.8 = 主动凑近同类 |
| 鱼苗最近邻中位 | **48px**（强化前 86px） | 体长 3px ⇒ 视觉上终于读得出"一群" |
| 老鱼独处 | 隔离度 **1.66**（5 个种子 1.66–2.45） | > 1.15 = 明显比全池平均更独 |
| 老鱼贴边率 | **0%** | 独处不能靠"被挤到墙角" |
| 卵 | 100% 在水里 · 100% 距岸 26–48px · 成窝率 100% | §8.2 步骤 3「水草/石上产卵」的退让口径 |

### 三条要注意的边界

1. **手绘鱼逐位不变**：`tools/trace-motion.js` 用 sha256 守「群游只作用于生态鱼」。
   手绘鱼没有 `stage` ⇒ 权重落回 0（内层分支跳过）、分离倍率落回 1（乘 1 在 IEEE754 下恒等）。
2. **老鱼判据不能再用「同阶段公平对照」**：老鱼中位 1–2 尾，而"最近邻"是**极值统计**，
   1–4 条鱼的比值方差极大（实测同一参数在 4 个种子上是 0.66 / 0.93 / 0.99 / 1.24，全是噪声）。
   改用**隔离度**（到最近一尾鱼的距离 ÷ 同一次采样里全池中位，对照组就在同一帧里）。
3. **群游要跑够时间才成型**：出生位置是随机撒的，聚合力的正反馈要几十秒才长成群。
   验收脚本每天跑 1800 帧（30 秒）运动、每 60 帧采一次样；
   初版每天只跑 300 帧（5 秒）⇒ 量到的是"刚出生随机散布"，鱼苗公平对照读出 1.02，
   看着像"群游没做"，其实是**尺子来不及**。

### 还没解决的（诚实清单，不是这次能修的）

- **种群规模**：软上限 30（§9.1）⇒ 池里 30–34 尾；参考画那一屏约 45 尾。属人口口径，不是渲染问题。
- **体量分布**：参考画的"小鱼"≈ 短边 4.9%，正落在我们的**成体**档（4.4%）；
  我们的鱼苗只有 0.33%、幼鱼 1.4%，而且半透明。**C 方案不改尺度口径**，
  所以"一池全是中等身量的鱼"这个观感**不会**出现 —— 我们给的是一条完整的体长金字塔。
- 层 10（flora 顺序倒置，鱼压在荷叶上）、层 3（焦散是死图）、层 11 风纹、层 16 池灯仍未动。
  层 12（明暗带）/ 13（碎光）/ 15（光池与光柱）/ 18（四角暗角）**已随 §10.5 光照场一起落地**，
  见 `docs/LIGHT-FIELD.md`。

| 颜色驱动 | 「颜色经 **`js/theme.js`** 参数驱动，**不硬编码**」 | `js/theme.js` **不存在**（全仓 0 命中）。颜色硬编码在三处：`landscape.js` 的 GLSL、`koi-renderer.js` 的 `COLOR_PALETTE`、`pond.js` 的 `drawWater/drawLotus` 里成串的 rgba 字面量 |

⇒ 「不硬编码」这条**结构性要求**没有落地。三套主题不是加三个配色表，而是要把散落的颜色抽成一张参数表 —— 属改造级工作量。

**顺带一条实测**：A 的水体平均 RGB ≈ `(102,153,119)`（R≈B，**青碧偏灰绿**），
当前实现 ≈ `(65,163,126)`（R 低 37，**翠青**），项目设计稿 ≈ `(61,147,120)`。
需求色板给的水色是 `#7FB3A8` = `(127,179,168)`，同样是 **R≈B 的青碧**。
⇒ 当前水色**整体偏青偏饱和**，与色板方向不一致（这一项需要 LUT 校准才能定量收口，此处仅记录现象）。
